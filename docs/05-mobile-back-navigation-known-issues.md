# 移动端系统返回：现有边界与已知问题

## 范围

本文记录已安装 PWA 或移动浏览器中，使用系统返回键、屏幕边缘返回手势时的当前行为。桌面浏览器的普通后退按钮不在本问题范围内。

## 当前实现

移动端每次加载已认证工作台时会先显示“进入工作台”入场层。用户点按后，应用才启用基于 History API 的返回守卫：

1. 图片预览优先关闭。
2. 非对话页返回时进入对话页。
3. 对话页首次返回显示“再按一次返回退出应用”，第二次返回放行给浏览器或 PWA 宿主。

## 已知问题

浏览器可能只在当前历史条目已发生页面内用户交互后才派发 `popstate`。因此从非对话页通过系统返回自动恢复到对话页后，该对话页对应的历史条目可能尚未获得用户激活。

在此状态下，用户继续立即使用系统返回，浏览器或 PWA 宿主可能直接退出，而不会派发可由 Web 应用拦截的事件；在对话页点按任意普通控件后，返回守卫又会恢复工作。

这不是仅靠追加 `history.pushState`、替换 History state 或重复监听 `popstate` 就能可靠解决的问题。Web 平台无法把系统级返回手势本身预先转换为当前历史条目的用户激活。

## 当前约定与临时操作方式

- 冷启动或刷新后，先点按“进入工作台”。
- 从其他页面自动回到对话页后，如需使用“再按一次退出”提示，先在对话页进行一次普通点按操作。
- 用户已明确暂不增加“回到对话页后再次轻点继续”的额外交互层；保留此限制，避免因解决返回问题而增加过多操作步骤。

## 后续决策边界

如需在所有场景下可靠拦截系统返回，需二选一：

1. 恢复“回到对话页后轻点继续”的页面内激活层。
2. 使用原生壳（例如 Capacitor）接管系统返回事件。

除非用户明确接受其中一种方案，后续不得继续以纯 History API 补丁承诺完全解决此问题。
